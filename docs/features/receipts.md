# Receipts — Frontend Feature Specification

**Status:** Planned / Phase 2

## Purpose

Provide access to immutable payment receipts generated by the backend.

The backend roadmap requires sequential receipt numbers, PDF generation, MinIO storage, and reprints that do not overwrite the original receipt. fileciteturn3file0

## Receipt list

Display:

- receipt number
- payment reference
- payment date
- amount
- created at
- download action

## Receipt detail

Show:

- receipt number
- payment information
- related property/tenant context
- generated timestamp
- download/reprint actions

## Reprint semantics

The UI should label the action as a reprint/view/download operation.

It must not imply that the original receipt is being edited.

If the backend returns a new Receipt record for a reprint, the UI should preserve the distinction.

## Acceptance criteria

- User can retrieve a receipt associated with an authorized payment.
- Download action does not mutate receipt data.
- Reprint behavior is clearly communicated.
- Missing/failed document retrieval produces an actionable error.
