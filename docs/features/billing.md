# Billing — Frontend Feature Specification

**Status:** Implemented (Phase 2) — see `src/app/admin/billing/page.tsx`

## Purpose

Display billing records generated by the backend recurring-billing engine.

The backend's actual state machine (`BillingRecordStatus`, `propnest-api`):

```text
pending
 ├──▶ overdue
 ├──▶ partially_paid
 └──▶ paid

overdue ──▶ partially_paid / paid / written_off
partially_paid ──▶ overdue / paid / written_off

paid, written_off: terminal
```

`pending` is set at generation — there is no separate `generated` status. There is no scheduled
transition between states either: `overdue`/late-fee evaluation only happens when
`evaluate_overdue` is explicitly called (no cron), and `partially_paid`/`paid` only happen as a
side effect of recording a payment against the record.

## Views

### Billing-record status panel

Shows the most recently generated/refreshed record for a lease:

- period (start – end)
- due date
- amount due
- balance (derived client-side from `status`/`overpaid_amount` — the backend doesn't expose a
  standalone "amount paid" or "balance" field, see `billingBalance()`)
- status

### Billing history

Table, per selected lease (`GET /billing-records/?lease_id=`):

- period
- due date
- amount due
- balance
- status

There is no "generated date" or "paid amount" column — `BillingRecord` deliberately has no
`amount_paid` field (see `propnest-api/docs/domain-model.md` §31); paid-to-date is only reflected
indirectly through `status`/`overpaid_amount`.

## Payment entry

Payment recording originates from a billing record: `PaymentForm` takes the lease's known billing
records and lets the user attach a payment to one via `billing_record_id`.

## Overdue state

Overdue is never client-calculated — it's shown exactly as returned by
`GET /billing-records/{id}` or `POST /billing-records/{id}/evaluate-overdue`. The backend
determines whether the grace period/late fees have made a record overdue.

## Acceptance criteria

- Billing records are displayed exactly as returned by the API.
- Balance is derived from `status`/`overpaid_amount` per `billingBalance()`, not from a
  backend-provided "amount paid" field.
- Overdue state is backend-authoritative.
- User can initiate payment recording from an eligible billing record.
- Generating ahead (multiple periods) is sequential and stops cleanly on the first failure,
  keeping whatever succeeded — see the "periods to generate" control.
